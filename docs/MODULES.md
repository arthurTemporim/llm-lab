# Modules

What each module in `modules/` is for, and the rules every module follows. Variables are in [CONFIGURATIONS.md](CONFIGURATIONS.md); how modules connect is in [ARCHITECTURE.md](ARCHITECTURE.md). Ports, versions and credentials are defined in each module's `docker-compose.yml` and `example.env`.

## Module contract

```text
modules/<name>/
├── docker-compose.yml   # required: joins the external "lang" network, pins image versions
├── docker-compose.gpu.yml # optional: NVIDIA override, base file must run on CPU (except GPU-only vllm)
├── example.env          # safe defaults with comments, every host port as a variable
├── .env                 # generated by `make create-envs`, git-ignored
├── Dockerfile           # optional: only when extending an upstream image (docling's manager/ builds a small helper)
├── README.md            # required: follows MODULE_README_TEMPLATE.md
└── <assets>             # optional: configs, flows, notebooks
```

Naming, Compose, env and integration rules are in [CONVENTIONS.md](CONVENTIONS.md). `scripts/check_conventions.sh` enforces most of them.

## Modules

### common-services

The foundation. Creates the shared network and runs Postgres (with pgvector), Redis and Garage (S3-compatible object storage). Its `.env` is the global env file that every module loads first. Always start it first. `make common-services` creates the `langflow`, `langfuse`, `litellm` and `hatchet` databases (with `vector`) on any volume. Redis runs with `noeviction` because Langfuse requires it.

### ollama

Pulls, runs and serves open-weight LLMs and embedding models, with its own API and an OpenAI-compatible one. Models are stored in a volume. Pull models with `scripts/ollama_pull_model.sh` (edit its list) or `docker exec ollama ollama pull <model>`. Uses the GPU when available.

### localai

OpenAI-compatible server for LLMs, embeddings, images and audio. Starts with no models: install them from its gallery (web UI or `POST /models/apply`). Requires an API key, generated into its `.env`. Uses the GPU when available, the CPU image otherwise.

### vllm

High-throughput server for Hugging Face safetensors models (chat, vision, embeddings, speech-to-text) with an OpenAI-compatible API. **GPU only**: it is the exception to the "base compose runs on CPU" rule, so the NVIDIA reservation is in its `docker-compose.yml` and there is no GPU override. Needs compute capability 7.5+ (not the Tesla P4), so `VLLM_GPU_ID` pins one card (set by `make gpu`). Serves one model per process: set `VLLM_MODEL` and `VLLM_EXTRA_ARGS` in `.env`.

### docling

docling-serve: converts PDFs, Office files, HTML and images to Markdown, JSON or text over HTTP (`/v1/convert/file`, sync or async), with a web UI at `/ui`. Layout, table and OCR models are baked into the image, so clients only upload files and need no Docling or PyTorch.

Two containers:
- **`docling`** is a small manager (built from `manager/`), and clients use it with the docling-serve API unchanged. It queues jobs (`DOCLING_MANAGER_CONCURRENCY` caps how many run at once for all clients), starts **`docling-worker`** (docling-serve) on demand through the mounted Docker socket, restarts it and retries on crashes, task failures or stuck conversions, and stops it after `DOCLING_MANAGER_IDLE_TIMEOUT` seconds idle to free VRAM.
- **`docling-worker`** uses `restart: "no"` so only the manager starts it. Like `litellm-init`, it is an exception to `restart: unless-stopped`.

The GPU override applies to the worker: it swaps in the CUDA 12.8 image and pins one Turing or newer card (`DOCLING_GPU_ID`, not the Tesla P4).

### openwebui

ChatGPT-style web UI with RAG, web search, code execution and image generation. Preconfigured for Ollama; add other OpenAI-compatible connections (LocalAI, LiteLLM) in the admin settings. The admin is created on the first start (`LAB_EMAIL` and the generated `WEBUI_ADMIN_PASSWORD`). Uses the GPU for local embeddings when available.

### langflow

Low-code visual builder for chains, agents and RAG. Built from a custom Dockerfile that adds extra bundles. Flows are stored in Postgres. `langflow.json` has example flows to import. In components use the container names of Ollama or LiteLLM, not `localhost`.

### notebooks

Jupyter playground with LangChain and the Ollama integration. Notebooks are bind-mounted so work stays on the host. Add Python packages in `requirements.txt` and rebuild. Includes a basic chain notebook and a RAG example. Runs without a token, so keep it local.

### litellm

OpenAI-compatible gateway in front of Ollama, LocalAI and cloud providers, with keys, budgets, routing, an admin UI and Prometheus metrics. Uses the `litellm` database in Postgres. At every start a one-shot `litellm-init` service registers all models pulled in Ollama, with per-model settings from `models.yaml`. Can send traces to Langfuse.

### langfuse

LLM observability: traces, sessions, prompts, evals and datasets. Runs a web app, a worker and ClickHouse, and uses Postgres, Redis and Garage from `common-services`. Set its secrets in `.env` before starting. `make langfuse` also checks that the Garage credentials match. See `modules/langfuse/README.md` for the full reference.

### hatchet

Hatchet Lite: durable task queue and workflow engine (engine, REST API and dashboard in one container). Workers connect over gRPC, register tasks and workflows, and Hatchet schedules, retries and records every run. Uses the `hatchet` database in Postgres. Set `HATCHET_PUBLIC_HOST` to the server's LAN IP when the dashboard or workers run on another machine. Worker tokens are created by `make hatchet-token` (also part of `make init` when hatchet is selected).

## Adding a module

1. Create `modules/<name>/` following the contract above and [CONVENTIONS.md](CONVENTIONS.md).
2. Write `docker-compose.yml` with the external network and a pinned image.
3. Write `example.env` with every variable commented.
   Write `README.md` from [MODULE_README_TEMPLATE.md](MODULE_README_TEMPLATE.md).
4. Add the name to `MODULES` in the `Makefile`. Targets `up-<name>` (or `<name>`), `down-<name>`, `build-<name>`, `logs-<name>`, `up-all`, `build-all`, `down` and `create-envs` then work. New databases go in `POSTGRES_DATABASES` (`common-services/example.env`).
5. Update the README module table and these docs (`MODULES`, `CONFIGURATIONS`, and `ARCHITECTURE` if it adds a dependency or flow).
6. Validate with `bash .claude/skills/validate/validate.sh <name>`, then start it for real.
